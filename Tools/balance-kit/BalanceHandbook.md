# 数值设计手册（Balance Handbook）

> **使用方式**：项目要定战斗数值、成长曲线、经济收支时，对 AI 说——
> 「读 `<本文件所在目录>\BalanceHandbook.md`，按它执行」
> 本文件所在目录即工具包根目录，下文称 `KIT_DIR`。
> 位置约定：`<工程根>/Tools/balance-kit/`，与 `Tools/touch-kit/`、`Tools/save-system/` 同级；
> 不纳入工程 git，由本工作区（可复用资源库）统一版本化。
>
> **这不是管线**：一份手册 + 三张 CSV 模板 + 一个校验脚本 + 三个可选 C# 模板，没有阶段链。

## 0. 三十秒判断表

| 症状 | 最可能的根因 | 先查什么 |
|---|---|---|
| 后期伤害/血量爆炸，数字多到看不清 | 成长曲线每级倍率过高，且没有分母 | 每级倍率是否 > 1.5；减伤公式是不是加法 |
| 打小怪要磨半天，或一刀秒一片 | TTK 没有验收标准，纯拍脑袋 | 用 `ttk` 命令反算，对照品类区间 |
| 玩家钱越攒越多，商店形同虚设 | 消耗口（sink）覆盖率 < 0.8 | `economy_flows.csv` 的覆盖率 |
| 玩家永远买不起第一件装备 | 价格锚点脱离产出速度 | 可负担时长（价格 / 每小时产出） |
| 防御堆到后面完全打不动 | 减法式 + 没有最低伤害 | 公式族选型、`minDamage` |
| 货币变成负数 / 突然清零 | 用 `int` 存货币，溢出 | 是否 `long` + `AddClamped` |
| 存档里的数值读出来差了 1 | 大整数走了 `float` | 是否超过 2^24 |
| 调了一个参数，别的地方全崩 | 一次改了多个变量，没有基线 | 是否记录了变更前的一组数 |
| 同样的暴击率，体感忽高忽低 | 独立随机没有保底 | 是否需要 PRD / 保底计数 |

## Step 1 先分清三层：哪些通用、哪些不通用

数值设计最容易走两个极端：一是到处找「通用数值模板」直接抄，二是认为「数值全靠手感」拒绝任何规范。都不对。正确做法是分三层：

| 层 | 是否通用 | 内容 | 本手册的处理 |
|---|---|---|---|
| ① 技术硬约束 | **完全通用** | int32/int64/float 上限、序列化精度、溢出、负数 | Step 2，必须遵守 |
| ② 方法论与验收标准 | **高度通用** | TTK、EHP、DPS、伤害公式族、成长曲线、产出/消耗、保底、可读性 | Step 3~8，按品类调区间 |
| ③ 具体数值 | **完全不通用的** | 移速 6 还是 8、Boss 5000 血还是 5 万、药水卖 60 还是 350 | Step 9~10，每个项目自己推导并存表 |

结论：**没有「通用数值表」，但有「通用数值工程」**。本工具包给的是第 ①② 层，第 ③ 层由每个项目用同一套表结构和校验脚本推导出来。

第 ③ 层不能通用的原因很具体：同样的 HP/伤害，换成 30 秒一关和 3 分钟一关、换成 1 倍镜和 4 倍镜、换成有付费和无付费，体感完全不同。**数值永远服务于体验目标，而不是反过来。**

## Step 2 技术硬约束（不遵守一定会出 bug）

### 2.1 类型与上限

| 类型 | 精确表示范围 | 用途 | 禁止 |
|---|---|---|---|
| `int` (int32) | ±2,147,483,647 | 关卡号、次数、小数值 | 货币、累计经验、总伤害 |
| `long` (int64) | ±9.22×10^18 | **货币、累计伤害、经验** | 无（除非要序列化到只支持 32 位的旧存档） |
| `float` | 整数精确到 2^24 = 16,777,216 | 位置、速度、动画参数 | 货币、伤害结算、存档数值 |
| `double` | 整数精确到 2^53 | 离线收益、长周期模拟 | 每帧热路径（性能） |
| 定点数 | 自定 | 联机同步、回放 | 单机表现层（没必要） |

三条铁律：

1. **货币一律 `long`**。`int` 上限约 21 亿，长线项目一件装备就能顶到。
2. **结算不用 `float` 累加**。`float` 在 1677 万之后 +1 可能不变化，伤害/经验越滚越大时会出现「打不死」和「经验不涨」。
3. **任何数值改动都进配置表**，不写死在代码里（与 `AGENTS.md` 的「数据驱动」一致）。

### 2.2 三个必设的保险

- **最低伤害** `minDamage > 0`：否则「防御 ≥ 攻击」时伤害为 0，目标永久无敌。
- **减伤上限**：乘法式天然 < 100%，但仍建议硬性留 10% 穿透，避免后期无敌坦克。
- **货币上限**：`AddClamped(current, delta, cap)`，超出就钳制并触发 UI 提示，绝不回绕成负数。

对应的现成实现见 `templates/NumericSafety.cs`。

## Step 3 从体验反推数字：TTK / EHP / DPS

数值不是「先定数字再看手感」，而是**先定体验，再反推数字**。

### 3.1 三个核心量

```
单次伤害   damage
攻速       aps（次/秒）
DPS        = damage × aps                （含暴击时用期望，见 4.5）
减伤率     m = def / (def + K)           （乘法式，K 为减伤常数）
有效血量   EHP = HP / (1 - m) = HP × (def + K) / K
击杀耗时   TTK = EHP / DPS = HP × (def + K) / (K × DPS)
```

`K` 的经验取法：**取「1 级角色的攻击力量级」**。攻击力 10 时 K=10，攻击力 100 时 K=100。K 太小 → 防御收益过强；K 太大 → 防御形同虚设。

### 3.2 品类参考区间（经验值，按项目实测校准）

| 品类 | 杂兵 | 精英 | Boss |
|---|---|---|---|
| 动作 / 平台 | 0.2~0.8s | 3~15s | 30~180s |
| 割草 / ARPG | 0.1~0.5s | 2~10s | 60~300s |
| 回合制 RPG | 1~2 回合 | 3~6 回合 | 8~15 回合 |
| 塔防 | 单波 10~30s | — | 单局 5~15min |

这些不是行业硬标准，是**验收锚点**：超出区间不一定是错，但必须有理由（例如「本作故意让杂兵很硬，强调走位」）。

### 3.3 反推顺序（不要跳步）

1. 定 TTK 目标（例如杂兵 0.4s、Boss 90s）。
2. 定玩家该阶段的 DPS（由攻击力 × 攻速得出）。
3. 反算目标 HP：`HP = TTK × DPS × K / (K + def)`。
4. 最后才调表现层（受击硬直、数字跳动、镜头震动）。

反算示例（可直接跑）：

```bash
python Tools/balance-kit/balance_check.py ttk --hp 500 --dps 120 --def 20 --tier elite
```

> 本项目 M3 战斗的原型值是 `HP 5 / 伤害 1 / 硬直 0.6s`（见 `specs/03-Combat/design.md`），
> 属于「先把命中链路跑通」的量级，不是最终数值。等敌人 AI（M4）接入后，
> 用本节方法按 TTK 目标重算，再回填 `CombatConfig` 与 `GDD.md` 第八节。

## Step 4 伤害公式三族

### 4.1 减法式

```
damage = max(minDamage, atk - def)
```

- 优点：玩家一眼看懂，「破防」感强。
- 缺点：线性、极敏感。防御 +10 可能让伤害从 30 掉到 20；后期必须靠数值膨胀抵消。
- 适用：短流程、单机、防御值区间窄（如 ±50%）的游戏。

### 4.2 乘法式（长线首选）

```
m      = def / (def + K)
damage = max(minDamage, atk × (1 - m)) = atk × K / (K + def)
```

- 优点：减伤率永远 < 100%，防御收益递减（每点防御的边际收益越来越小），天然抗膨胀。
- 缺点：前 10 点防御收益明显，后面要堆很多才涨 1%，需要 UI 明确展示减伤率。
- 适用：RPG、ARPG、长线运营、有装备成长线的项目。

### 4.3 混合式

```
damage = max(minDamage, (atk - 0.5 × def) × (1 - m))
```

- 先扣一半防御给「破防感」，再吃乘法减伤保曲线。
- 缺点：两个参数（flatShare、K）互相影响，调参成本翻倍。
- 适用：既想要减法手感、又怕后期崩的中长线项目。

### 4.4 选型表

| 项目特征 | 建议 |
|---|---|
| 流程 < 2 小时、数值区间窄 | 减法式 |
| 有等级/装备成长、要做 10 小时以上 | 乘法式 |
| 既要破防手感又要长线稳定 | 混合式（先按 0.5 起步） |
| 联机 / 回放 / 需要确定性 | 定点数 + 乘法式 |

**不要混用**：同一个项目里，玩家打怪用减法、怪打玩家用乘法，玩家永远算不清自己有多硬。

### 4.5 暴击与期望

```
暴击期望 = damage × (1 + critRate × (critMultiplier - 1))
DPS      = 暴击期望 × aps
```

调平衡时**永远用期望值算 DPS**，不要用「暴击那一下」的数字。否则暴击率 5% 的角色会被高估。

## Step 5 成长曲线

### 5.1 四种曲线

| 曲线 | 公式 | 每级变化 | 适用 |
|---|---|---|---|
| 线性 | `v = base + step × (n-1)` | 绝对增量恒定，倍率递减 | 动作游戏血量、固定长度关卡 |
| 多项式 | `v = base × (1 + n)^p`（p=1.5~2） | 倍率递减但绝对值加速 | 中长线、放置类 |
| 指数 | `v = base × r^(n-1)` | 倍率恒定 | RPG 等级、装备强化、长线养成 |
| 对数/递减 | `v = base × (1 + k × ln n)` | 快速递减 | 熟练度、收益递减型属性 |

### 5.2 每级倍率的红线

- `r = 1.05~1.15`：RPG 等级成长的常见区间，30 级约 4~70 倍。
- `r = 1.15~1.2`：可以，但**必须同步抬高分母**（防御 K、怪物 HP 曲线），否则 TTK 会失控。
- `r > 1.5`：每 2 级翻倍，20 级就是 3000 倍。除非做「指数对指数」，否则一定崩。
- `r < 1.0`：数值倒退，只应出现在「满级后转生」这类明确设计里。

校验脚本会对 `hp/atk/def` 的每级倍率做 1.0~1.5 的区间检查。

### 5.3 封顶与反算

指数曲线一定要有上限或软上限，否则 3 位数等级就会超过 `long`。

```
达到上限 cap 所需等级：n = 1 + ln(cap / base) / ln(r)
```

示例：`base=100, r=1.12, cap=1e9` → 约 143 级封顶。跑：

```bash
python Tools/balance-kit/balance_check.py curve --base 100 --step 1.12 --levels 30
```

软上限的常见做法：超过阈值后倍率从 1.12 逐级降到 1.02，而不是硬砍成 0 成长。

## Step 6 经济：产出（faucet）与消耗（sink）

### 6.1 每种货币都必须有这两列

| 方向 | 含义 | 例子 |
|---|---|---|
| `faucet` | 系统凭空产出 | 击杀掉落、任务奖励、离线收益 |
| `sink` | 系统回收销毁 | 商店购买、修理费、强化消耗、税、门票 |

**只有 faucet 没有 sink 的经济必然通胀**——玩家钱越来越多，价格就失去意义。

### 6.2 覆盖率

```
覆盖率 = Σ(每条 sink 的 amount × per_hour) / Σ(每条 faucet 的 amount × per_hour)
```

| 覆盖率 | 状态 | 处置 |
|---|---|---|
| < 0.8 | 通胀：钱越攒越多 | 加 sink（修理/税/消耗品/限时商店）或降 faucet |
| 0.8~1.2 | 健康 | 保持，并关注中位余额是否稳定 |
| > 1.2 | 通缩：玩家持续破产 | 提 faucet 或降价格 |

注意：这是**长期均衡**指标。前期（0~2 小时）允许覆盖率偏低，让玩家先攒出第一桶金；后期再靠大额 sink（装备强化、房产、抽卡）回收。

### 6.3 可负担时长

```
可负担时长(小时) = 目标商品价格 / 每小时总产出
```

| 时长 | 体验 |
|---|---|
| < 1 分钟 | 太便宜，购买没有决策感，只是走过场 |
| 5 分钟~2 小时 | 健康区间，玩家有明确目标 |
| > 40 小时 | 太贵，前期挫败，除非是终局内容 |

用 `price_anchor` 列标出关键商品（第一把武器、第一瓶药），脚本会自动算。

### 6.4 通胀/通缩诊断

| 观察到的现象 | 数据特征 | 处方 |
|---|---|---|
| 商店没人买 | 玩家余额中位数持续上升 | 加 sink，而不是简单涨价 |
| 玩家只买最便宜的 | 高价位商品可负担时长 > 40h | 增加中期产出，或做分期/租赁 |
| 后期钱没处花 | 满级后 sink 全部失效 | 增加终局 sink（洗点、外观、捐赠） |
| 经济一夜崩盘 | 某个活动 faucet 没有上限 | 给 faucet 加每日上限，而不是事后回收 |

## Step 7 随机与保底

### 7.1 独立随机的长尾

独立随机下，`n` 次都不触发的概率是 `(1-p)^n`。要有 95% 把握至少触发一次：

```
n = ceil( ln(0.05) / ln(1 - p) )
```

| 标称概率 | 95% 把握所需次数 | 体感 |
|---|---|---|
| 10% | 29 | 可接受 |
| 5% | 59 | 偏差明显 |
| 1% | 299 | 必须加保底 |
| 0.1% | 2995 | 不加保底就是事故 |

### 7.2 三种做法

| 做法 | 原理 | 适用 |
|---|---|---|
| 独立随机 | 每次独立掷骰 | 掉落材料、低价值随机 |
| PRD（伪随机分布） | 连续不触发时逐步提高概率 | 暴击、需要「手感稳定」的判定 |
| 硬保底 | 计数到 N 必出，出后清零 | 抽卡、稀有掉落、关键道具 |

原则：**高价值 / 高情绪波动的随机必须加保底**；低价值材料可以纯随机。保底计数器要进存档。

## Step 8 数字的可读性

玩家能一眼处理的数字大约是 **3~4 位有效数字**。

| 场景 | 建议 |
|---|---|
| 战斗数字 | 4 位以内直接显示；超过用 K/M/B/T |
| 伤害跳字 | 超过 5 位就缩写，否则会糊满屏幕 |
| 属性面板 | 显示整数，不显示 `123.0000001` |
| 百分比 | 保留 1 位小数，减伤率向上取整展示（避免「显示 50% 实际 49.6%」的争议） |
| 单位切换 | 同一局内不要换单位（前 10 分钟用 K，后面突然变 M 会让玩家迷失） |

`templates/NumericSafety.cs` 的 `FormatCompact` 提供 1.2K / 3.4M / 5.6B / 7.8T 的显示格式，**只用于 UI，不参与结算**。

## Step 9 落表：CSV → ScriptableObject → 运行时

### 9.1 三张表（`KIT_DIR/tables/` 是示例，复制成项目的表）

#### `combat_units.csv`

| 列 | 含义 | 必填 |
|---|---|---|
| `id` | 唯一 ID，进过存档不能改 | 是 |
| `name` | 显示名 | 否 |
| `role` | 职业/定位 | 否 |
| `tier` | `trash` / `elite` / `boss`，决定 TTK 区间 | 是（不填则不查 TTK） |
| `hp` | 血量 | 是 |
| `atk` | 攻击力 | 否 |
| `def` | 防御 | 是 |
| `aps` | 每秒出手次数 | 否 |
| `crit_rate` | 暴击率 0~1 | 否 |
| `crit_mult` | 暴击倍率，≥1 | 否 |
| `dps_ref` | **玩家在该阶段的参考 DPS**，用于 TTK 核算 | 是 |
| `notes` | 备注 | 否 |

#### `progression_curve.csv`

`level, exp_to_next, hp, atk, def, gold_reward`。用来校验曲线是否单调、每级倍率是否越界。

#### `economy_flows.csv`

| 列 | 含义 |
|---|---|
| `id` | 唯一 ID |
| `currency` | 货币名（gold / gem / ...） |
| `direction` | `faucet`（产出）或 `sink`（消耗） |
| `amount` | 单次数量 |
| `per_hour` | 每小时发生次数 |
| `price_anchor` | 关键商品价格（可空），用于算可负担时长 |
| `notes` | 备注 |

### 9.2 文件放哪

| 内容 | 位置 | 原因 |
|---|---|---|
| 权威数值表（CSV） | `<工程根>/Docs/Balance/` | 可 diff、可评审、不进 Assets |
| 运行时资产（SO） | `<工程根>/Assets/Settings/Balance/` | Unity 序列化、Addressables 可加载 |
| 校验脚本 | `<工程根>/Tools/balance-kit/` | 不参与编译 |

**CSV 是权威，SO 是产物**。改数值改 CSV，重新导入生成 SO，不要两边手改。

### 9.3 脚本用法

```bash
# 1) 生成示例表（已有文件会跳过，加 --force 覆盖）
python Tools/balance-kit/balance_check.py init Docs/Balance

# 2) 体检（0 error 即通过）
python Tools/balance-kit/balance_check.py check Docs/Balance

# 3) CI / 出包前卡口（warn 也算失败）
python Tools/balance-kit/balance_check.py check Docs/Balance --strict

# 4) 反算 TTK
python Tools/balance-kit/balance_check.py ttk --hp 500 --dps 120 --def 40 --tier elite

# 5) 生成成长曲线
python Tools/balance-kit/balance_check.py curve --base 100 --step 1.12 --levels 30

# 6) 按减法式体检
python Tools/balance-kit/balance_check.py check Docs/Balance --formula sub
```

输出是「文件 / 行号 / 原因」，可直接贴进 issue。退出码 0/1，可接 CI。

### 9.4 导入 Unity

CSV 本身不进 `Assets`；推荐流程：

1. 编辑器脚本读 `Docs/Balance/*.csv`（`File.ReadAllText` + `CsvTable.Parse`）。
2. 每个 `id` 生成/更新一个 ScriptableObject（`CreateAssetMenu` + `AssetDatabase.CreateAsset`）。
3. 生成的 SO 放 `Assets/Settings/Balance/`，由 Addressables/YooAsset 加载。

运行时读表也可以直接用 `templates/CsvTable.cs` 解析 `TextAsset`，但**权威数据仍以 CSV 为准**，避免「代码里改了一半、表里没改」。

## Step 10 调参流程（一次只改一个变量）

1. **写目标**：这一轮要解决什么体验问题（例：杂兵 TTK 从 1.2s 降到 0.5s）。
2. **记录基线**：把当前一组数复制到 `GDD.md` 的变更记录，注明日期。
3. **改一个变量**：只改攻击力或只改血量，不同时改。
4. **跑校验**：`balance_check.py check`，确认没有越界。
5. **实机验证**：至少打 10 只同类怪，记录实际 TTK。
6. **回填**：把实测值写回 CSV 与 `GDD.md` 第八节，注明「实测校准」。

禁忌：

- 不要凭「感觉快了/慢了」直接改表，先量 TTK。
- 不要在 Play 模式里改 Inspector 就宣布完成，退出 Play 后改动会丢（见 `AGENTS.md`）。
- 不要一次改 5 个参数然后说「整体调好了」，出问题无法归因。

## Step 11 反面清单

1. 用 `int` 存货币，或把货币/伤害存进 `float`。
2. 伤害公式没有 `minDamage`，高防目标永久无敌。
3. 同一个项目混用多套伤害公式。
4. 成长曲线每级 ×1.5 以上，还不同步抬分母。
5. 只有产出没有消耗，或只在开局配了 sink。
6. 关键随机没有保底，还对外宣称「概率 1%」。
7. 数值直接写死在代码里，或只改 Inspector 不落表。
8. 战斗数字超过 6 位还硬显示，糊满屏幕。
9. 用「暴击那一下」的伤害算 DPS，而不是期望值。
10. 改数值不记录基线，出问题无法回滚。
11. 让 UI 持有并修改游戏数值（UI 只读、只抛事件）。
12. 拿别的项目的数值表直接套——包括本工具包的示例表。
